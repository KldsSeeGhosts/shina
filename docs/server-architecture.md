# Headless server and clients

## Implementation status

Slices 1, 2 and 3 are integrated. Slice 4 is implemented, with native Windows fixture validation; real tailnet rollout remains the parent's responsibility. Slice 5 is implemented with native macOS fixture validation, as detailed below. Legacy mode remains the default for profiles that have not migrated. `--server-client` opts into server ownership; once `state.sqlite` exists, plain desktop launches automatically attach to or supervise the local server as clients. The same binary's `serve` command owns the existing reducer, subprocess workers, MCP queue and background scheduling. `runtime.rs` serializes commands and ticks without initializing artwork, portrait animation or image caches. Reducer extraction remains incremental.

`server_lock.rs` uses the never-unlinked `server-owner.sqlite` exclusive transaction in both execution modes. `server_auth.rs` publishes loopback discovery only after recovery/listener setup, with stable server and epoch IDs, a fresh instance ID and a 256-bit OS-random bootstrap token. Windows applies a protected current-user-only DACL without changing ownership, auditing privileges or authentication. Bootstrap exchange now issues durable device credentials. Origins remain refused.

`database.rs` and `migrations/001.sql` add `state.sqlite`, with bundled SQLite, WAL, `synchronous=FULL`, integrity checks and serialized access. Schema 1 has `metadata`, `documents`, `projection`, `events`, `command_receipts`, `effect_outbox` and `devices`. The versioned documents retain existing index, task, memory and routine schemas, including runtime inputs and intents. This avoids changing their recovery algorithms during storage migration. Receipts also have an independent device/command primary key; their deduplication history is not trimmed.

The one-time import validates supported schemas, IDs, references and submitted images before committing any imported records. It imports the index and its tasks, server-owned pending inputs and keep-awake policy, memory, routines and the Honcho outbox in one transaction. It verifies stored document contents and source SHA-256 hashes before recording `legacy-import-v1`. All source files stay unchanged. Client drafts/layout are not imported into server documents. Existing pre-index project/collision migration still runs when needed. A verified `state.sqlite.import-v1.bak` follows the import; `Database::backup` creates non-overwriting, verified backups including WAL contents for future updates. Unknown/newer schemas, damage and failed imports block startup or further writes. They never select JSON as a fallback.

Legacy mode deliberately keeps JSON for unmigrated profiles. Once `state.sqlite` exists, even after a failed import, desktop setup selects client mode automatically without loading the legacy index or starting legacy stores. Direct legacy loading still refuses execution and saving. The client reports server recovery or import errors rather than falling back to JSON. Legacy files remain unchanged; the original UI file remains a read-only source for the first client's drafts. `--server-client` remains supported but is no longer required for migrated desktop launches. Reverting requires an explicit matched-profile restore; Shina does not merge newer database state back into old JSON.

`outbox.rs` captures harness pipe sends during each reducer batch. One transaction commits the state documents, projection patch/event, receipt and pending effects before the worker claims or sends them. A failed commit discards in-memory dispatch and blocks writes. Process-bound pending/dispatching effects become interrupted after restart, never re-enqueued. A receipt associated with such an effect also becomes interrupted. Accepted input that was waiting for startup or recall remains a durable intent, not proof of provider execution. Existing Pi history and task delivery IDs reconcile acceptance and completion. ACP without history retains its saved transcript and reports interrupted work. Honcho turns commit with their stable-ID outbox records; its worker reads only committed turns and retains the existing remote metadata reconciliation.

Protocol 1.2 combines slice 2's 1.1 additions with coordinated restart and minor negotiation. Hello returns the negotiated minor and its capabilities. Protocol 1.1 adds typed `set`/`remove` patches and a monotonic workspace cursor. Subscribe with `lastSeq` and `epoch`. Replay requires a contiguous retained range, at most 128 events and 1 MiB encoded, following KSG's `decideThreadResume`; otherwise the server sends a snapshot. The event log retains the latest 1024 sequences. The latest-value watch channel coalesces slow readers, which resume or fall back without blocking the runtime; socket sends have a two-second deadline. Protocol 1.0 clients retain full-snapshot compatibility, with the former 2 MiB cap raised to 64 MiB. Older clients without PID registration must close before updating and receive explicit upgrade guidance.

Workspace projections omit transcript payloads and include per-thread `historyRevision`. Oversized workspace metadata uses `subscription.snapshotPage`. Protocol 1.7 advertises `history-items` and replaces the old revision/offset history method. A peer without this baseline receives an explicit "Update required" state instead of a paging fallback.

Thread transport ports KSG Code's scoped snapshot plus incremental item stream. `thread.subscribe` accepts `threadId`, optional `afterSequence` and `streamEpoch`, and `byteBudget`. It registers the selected thread, replays retained events, and returns `kind: synchronized`, or returns the first fragment of a recent scoped snapshot with `kind: snapshot` and `streamEpoch`. Each history page contains `threadId`, `snapshotSequence`, `historyRevision`, `items`, non-array `fields`, `nextCursor` and `hasMoreHistory`. Rows carry `sourceThreadId`, `sourceItemId`, `field`, `ordinal`, `position` and `item`. The client merges history by identity, preserves newer live records and removals, and renders each existing Shina array in ordinal order. It loads older pages without replacing the installed view.

`thread.history` accepts `threadId`, opaque `historyCursor` for an older window, optional `fragmentCursor`, and `byteBudget`. A history cursor identifies the source item and position, not a content hash. Streaming does not invalidate it. Windows contain at most 75 rows and stop at the byte budget, except that one oversized row must make progress. Shina retains the existing 64 KiB default and 256 KiB maximum data-fragment budgets, including for that oversized row. Only fragmentation needs a connection-local immutable lease. Leases have a count limit of four, a total serialized-byte limit of 128 MiB, and a 30-second idle expiry. Fragment results contain `encoding: utf8-json`, `data`, `nextFragment` and `totalBytes`. Error `-32010` means the lease expired or was evicted. The client automatically retries one scoped snapshot, reports `history retry 1/1` through the existing error channel, and stops with the older view intact after a second failure. `historyRetry` records the count, limit, cumulative full restarts, error and stopped state. No UI layout changes accompany it.

`thread.stream` notifications contain the process-specific `streamEpoch`, `threadId`, monotonic `sequence`, `kind: event`, `historyRevision` and an ordered `events` batch. `item.updated` upserts a complete row, `item.removed` removes an identity, and `fields.updated` replaces non-array history fields. A committed workspace sequence groups all changes atomically. Sequences need not be contiguous for a scoped thread. Large notifications use `thread.streamPage` UTF-8 fragments. Replay admits at most 128 item events and 1 MiB encoded data. The server retains at most 1024 batches and 4 MiB for replay. A pruned, future or oversized replay requests a new scoped snapshot. An idle cursor at its thread's high-water mark still resumes. History reads never advance the live cursor. The native client allows one history request in flight, ignores duplicate stream sequences, and keeps applying live items while it reads older pages. A server restart changes the stream epoch and requires one fresh scoped snapshot.

KSG has durable turn-item identities and persisted domain events. Shina's existing message records have neither. To keep persistence formats unchanged, its transport assigns process-local item IDs, preserves exact matches across moves and slot identities across streaming edits, and indexes existing committed snapshots for replay. Intrinsic tool/work IDs take precedence. The process epoch fences these wire-only identities on restart. This transport replay is deliberately not a new durable event log. KSG admits an oversized item in one history response; Shina instead fragments the scoped response using the bounded lease above to preserve its hard data-fragment limits. There is no revision-tail RPC or full transcript download on each live revision.

Version skew follows KSG's forward-compatible contracts. New optional fields do not change the baseline capability. Unknown stream kinds and event types advance the replay position without changing known records. Unknown row fields are ignored, but malformed known records still fail validation. Missing `history-items` reports "Update required" and error `-32012`, not an indefinite loading state. The native client's history cache, individual history and stream reassembly, and pending snapshot-event buffer each retain a 64 MiB limit. Authenticated `GET /v1/blobs/{id}?offset=0&limit=65536` returns bounded image-file bytes with `x-blob-length` and `x-next-offset`; paths cannot escape the attachments directory.

The desktop attaches first or supervises its own `serve` child with 0.5 to 10 second backoff. Quit stops only that owned child, with five seconds before termination. An attached headless server remains alive. Windows tray opt-in keeps the desktop alive after an idle close.

Slice 3 implements `shina service install|uninstall|status|start|stop` in `service.rs`, ported from KSG's service and boot-service modules. `maintenance.rs` owns leased prepare/cancel/commit transitions. Runtime hooks check existing thread, queue, approval, clone and routine blockers, flush before preparation, fence all new mutations and skip reducer ticks and routine dispatch while draining. The shared database dispatch gate also pauses harness effects and the asynchronous Honcho outbox, including health requests. Fencing and claiming share one lock. An already claimed effect cancels preparation until it settles, rather than being interrupted. Startup validation applies the same gate before workers start. Local clients receive `server.draining`, flush their own stores and acknowledge with `server.clientReady`; save failure cancels. A preparation expires after 30 seconds without stopping work. `server.commitRestart` requires every registered local client's acknowledgement, flushes again and broadcasts `server.restarting` before idle-process shutdown. All maintenance RPCs use durable device authentication and recheck revocation and maintenance grants in the runtime. Bootstrap exchange remains loopback-only; only an unpaired local connection's registered PID may acknowledge its saved drafts. Remote clients reconnect without acknowledging local PIDs. The service CLI and helper reuse a protected, persistent maintenance-device credential.

The separate known-working helper waits for local process handles, including the service launcher, and the server owner lock before replacement. It requires a final-save acknowledgement for the prepared update ID. It retains a SQLite-consistent and JSON state backup, reuses Windows `ReplaceFileW` and macOS atomic bundle exchange, restarts the installed service or independent `serve`, checks authenticated readiness and expected binary version, then reopens clients. A validation marker fences dispatch in the replacement until `server.validateRestart`. A desktop-owned server uses a paused validation process, then reopened desktops spawn and supervise their own child as before. Updating does not opt the desktop into an always-on service. Startup failure restores the previous binary and its matched state, preserving the failed schema separately. Backups remain for rollback. The server also backs up before opening runtime state on a binary-version change, before slice 2's schema migration can run.

### Slice 4, paired multi-server clients

Protocol 1.4 advertises `filesystem-browse`. `filesystem.browse` requires `read` and returns one host-resolved directory, its parent and at most 200 directory entries with host-owned paths. Empty paths and `~` use the server user's home. The optional `partial` flag filters a parent directory for the folder palette. Unreadable directories report a path-free error. Clients of older servers retain a typed path field. `project.put` accepts `createFolder` under `operate`, creates missing parents, then canonicalizes. Unknown protocol methods fail authorization instead of inheriting `operate`.

`peer.rs` discovers Tailscale addresses through bounded `tailscale status --json`, following KSG's `packages/tailscale`. `serve --tailnet` and `service install --tailnet` explicitly add listeners on validated self addresses only. Default startup remains loopback. IPv4 requires `100.64.0.0/10`; IPv6 requires `fd7a:115c:a1e0::/48`. An injected address-source test rejects wildcard, loopback, LAN and public binding. Remote routers refuse bootstrap exchange and unpaired credentials. Origins remain refused on every endpoint. Native clients resolve and pin only loopback/tailnet destinations and refuse proxies and redirects.

`shina pair` creates a 48-bit OS-random code, valid for five minutes, with single-use consumption and five attempts per minute across the host. Only a local maintenance device can mint it. `shina link <host> <code>` exchanges it for a durable user-device credential. Schema 2 adds `device_grants`, after a verified pre-migration backup, and migrates existing local devices without making them remote-capable. Paired devices have `read`, `operate` and `approve`, but no `maintain` or `peer-delegate` grant. The runtime checks grants again before dispatch, including maintenance. Local PID registration excludes paired clients. Peers and MCP agents cannot mint credentials or approve through their thread-bound credentials.

Inbound listing/revocation uses `shina devices [revoke <device-id>]`. Outbound listing/revocation uses `shina links` and `shina unlink <server-id-or-host>`. Unlink requires acknowledged remote self-revocation before removing the local secret. An offline unlink reports failure and retains the link. Explicit re-pairing replaces a revoked credential, or revokes the previous active one before replacement. Secrets live under the protected host profile, outside repositories, never in logs or durable-token argv. Windows uses a protected current-user-only DACL; Unix uses private directories and mode 0600 credential files.

The desktop supervises only its local server. Each linked server has a separate connection worker, replay cursor, transcript reassembly, reconnect backoff and last-known projection. Persistent caches belong to the reserved client draft slot. Client identity is the server UUID paired with the server's thread ID; the UI facade installs only the selected server's records. Other servers remain visible in sidebar groups. Switching retains server-separated thread editors, tabs, scopes and pending receipts. This avoids rewriting existing numeric server-owned IDs and captain relationships. Backend subprocess dispatch deliberately remains `local` within each owning server. Remote directories come from that server's projection, and the client never normalizes or probes remote project paths.

The composer selector ports KSG's `BranchToolbarEnvironmentSelector` and `ComposerControl` xs spacing. The linking dialog ports `settings/AddEnvironmentDialog` and authorized-client controls. Sidebar machine labels follow `sidebar/SidebarThreadRow`. Offline servers keep cached read-only views and never redirect or queue commands, including approvals, on another host. New work starts on Local by default. Cross-server captain delegation remains slice 5.

New conversation drafts are device-owned records until Send. Retargeting an unsent draft moves its editor and image references to the chosen server, then asks for one of that server's projects or no project. It does not send `thread.create`. Send promotes the draft through a receipted creation and submits its content to that server, even if the user navigated elsewhere before its receipt. Selection waits for the owning server's projection. Started conversations keep a disabled machine indicator. The Add workspace palette shares local and remote browsing, and project receipts select a projected project rather than a thread ID.

Authenticated image uploads use create, offset-checked chunk writes and commit. Uploads are device-bound, expire after five minutes, and enforce a 10 MiB image limit, bounded chunks and bounded concurrent staging. Commit verifies SHA-256 and existing image-decoder limits before promotion. Existing eight-image and 20 MiB prompt limits still apply. A command carries only committed blob metadata; its receipt hash remains stable across reconnect. Ordinary client filesystem references are refused for remote sends. Remote image reads use slice 2 paging and content-addressed local caches.

One-process loopback fixtures simulate three servers and test pairing, expiry, reuse, throttling, grants, remote bootstrap refusal, create/view/stop, path isolation, both revocation directions, uploads and independent reconnect/replay. Headless Rune tests exercise the selector, labels and dialog at 620, 960, 1280 and 1920 px. A real two-process Windows check uses separate temporary profiles, CLI pairing/linking, remote create/start/view/steer/stop and acknowledged unlink, with fake Pi and no provider calls. Native Windows validation passed `cargo build`, `cargo test`, `cargo fmt --check` and `cargo clippy --all-targets -- -D warnings`, with 530 unit tests and 17 process integration tests passing; nine existing opt-in tests remain ignored. No tailnet port or real machine was paired during implementation. See README's "Linking machines" for exact rollout commands for Windows, both Macs and Ubuntu. Native macOS/Linux service activation and the four-machine tailnet rollout still require host validation.

### Slice 5, captain delegation and sync

Protocol 1.5 advertises `peer-delegation`. `peer.rs::link_peer` redeems `shina pair --peer` codes, using the existing five-minute, single-use, host-throttled pairing flow. Only a local maintenance credential can mint codes or manage outbound peers. Schema 3 adds the `peers` metadata table after the existing verified backup procedure. Durable peer credentials remain in protected `peers/<server-id>/credential.json` files, outside projections, logs and argv. `peer unlink` waits for remote self-revocation before removing a link; an unreachable target keeps its credential. Client links and peer links remain separate.

The new credential has exactly `read` and `peer-delegate`. `Database::authorize` denies ordinary subscriptions, history, blobs, filesystem browsing, uploads, approvals and maintenance to peers. Only `hello`, device-scoped receipt lookup, self-revocation and the explicit peer methods are available. `peer.capabilities` lists host projects with git remote identities, harnesses and models. `peer.thread.launch`, `send` and `stop` use device-scoped durable command receipts. The target records the authenticated peer device and the origin server, machine label, parent thread, task and captain. Every peer thread operation verifies that device. Linked workers cannot delegate, control other work or write captain memory through MCP.

`remote_tasks.rs` follows KSG's `RemoteDelegation`, `PeerForwarding` and link-origin rules. A home task retains its target server/thread, exact launch command, follow-up command, owed stop and stable stop command, retry error and deadline. The runtime dispatches network work only from previously committed task state, outside the reducer and behind the maintenance dispatch gate. Identity probes and authenticated calls use the same checked numeric address. Transport failures retry from two seconds to five minutes without failing the task. Revocation, a removed link, an unknown thread or a rejected launch ends following. Authentication denial stops credential retries.

`delegate_task.target.machine` selects a linked server by id, host or unambiguous label. `workspace` names that server's project by id or path. Explicit selectors still require a git remote matching a project in the caller's scope. Without a selector, the caller's git remote must match exactly one project; ambiguity or no match returns the available projects. Earlier captain homes cannot delegate. The target revalidates the selected harness and model, and preserves the existing local worker access-mode rule. Home capacity limits still queue more than three running workers and refuse more than eight unfinished tasks. The remote thread is an ordinary target-owned worker; the home thread is metadata and a result excerpt, never a local fallback process.

`peer.thread.status` reports target-owned questions without forwarding them to the parent. `peer.thread.read` atomically acknowledges a final result with its receipt before the home completes it. Result delivery then uses the existing delivery marker and parent acceptance check. Home restart retains command IDs and resumes open followers and owed stops. Recovered results stay held until a user turn or explicit result resume. Target recovery reads saved worker history without replaying a brief. Essential memories enter the brief as read-only data; successful-turn proposals return for captain review and never commit to home memory automatically.

Crew cards and tray chips port KSG's `V2LifecycleRow` and `ThreadRelationshipsControl`, with the existing sidebar machine tag and Departure Mono status words. A client link opens the target thread directly; otherwise the home shows the result and its machine. Target workers show their delegated origin in the parent bar. The Linked machines dialog adds outbound peers and local-maintenance linking controls with the existing fields, palette and frames.

Validation uses one-process loopback servers, deterministic reducer recovery tests, headless layouts at 620, 960, 1280 and 1920 px, and real `serve` processes with fake Pi in temporary profiles. The process fixture suspends only its temporary target server on Unix, restarts home while the target is offline, resumes the target, then repeats home recovery with cancellation still owed. Native macOS validation passed `cargo build`, `cargo test` and `cargo fmt --check`, with 723 unit tests and 19 process tests passing; ten existing opt-in unit tests remain ignored. No real machine or provider credential is paired. Native Windows and tailnet rollout validation remain separate host checks.

## Decision and evidence

### Protocol 1.6, linked-machine updates and settings

Minor 1.5 remains reserved for cross-machine delegation. Minor 1.6 adds `linked-updates`, `server.updateStatus` and the receipted `server.requestUpdate`. `protocol::method_grant` maps only those two methods to `update`. Paired devices do not receive it by default. `devices.grant` and `devices.revokeGrant` accept only the `update` grant, require `maintain`, reject paired callers in the runtime, and refuse remote-listener calls even with a maintenance credential. The CLI exposes `devices grant <id> update` and `devices revoke-grant <id> update`. The local authorized-device roster has the same switch. Existing grants and revocation remain unchanged.

The existing `read` grant still permits `server.status`; this change does not broaden or remove it. An `update`-only credential cannot call that method or any maintenance method. Local, unpaired maintenance credentials may use the two update methods without a separate update switch.

`fleet_update::ServerUpdates` owns one target-side attempt. `RuntimeState::command` validates blockers and the durable per-device rate limit, then commits the receipt and `update_audit` row before starting its worker. Schema 4's migration takes the existing verified backup first. Authenticated grant denials and other refusals also enter the audit table but do not consume the accepted-request limit. Duplicate command UUIDs return their receipt without launching another attempt. An accepted request consumes ten minutes even if checking fails or finds no newer release.

The caller supplies no release selection. `update::request_latest` uses the target's existing release check, private-repository `gh` login, asset validation, checksum verification and coordinated helper. Unknown caller fields, including versions, do not affect selection. A development checkout cannot advertise self-update. Linux requires a matching service installation. The shared local/remote blocker includes thread startup, queues, approvals, routines, clones and queued/running delegated tasks. The helper checks again after download, so newly started work cancels preparation rather than being interrupted.

The helper writes `updates/outcome.json` with the request ID, tag, success and specific failure reason. It records replacement failures before rollback reopens clients, then records the final result after the helper sequence. This file stays outside the matched-state backup. The server reads it at startup and while running, updates the audit record, and includes `updateStatus` and `updateNotice` in durable projections. Reconnecting clients learn success and rollback through ordinary replay/snapshot synchronization. The remembered failed-release policy remains target-local; the narrow update grant cannot clear it.

If the server dies during release preparation before a detached helper takes ownership, startup marks that accepted audit entry interrupted. It reports failure rather than repeating a download or leaving a client waiting forever. Revoking a grant blocks new requests; it does not cancel an update the target already accepted.

`fleet_update::Fleet` follows KSG Code's `useUpdateEverything` and `updateEverything.logic`. It plans one row per direct linked connection, skips offline or ineligible machines, and submits independent requests in parallel. It never creates a fleet endpoint, retries offline work or broadens the grant to maintenance. It follows the target's request ID through reconnect and waits for remote handoff or failure before local restart. Closing its dialog leaves accepted target-side work alone.

Desktop restart checks read Local's blocker even when the open conversation belongs to another machine. A busy remote thread cannot prevent an otherwise idle local update. Unsaved rename/captain editors still block closing the window.

`settings_ui.rs` ports KSG's settings navigation, search and row structure into the Pixel Voyage dialog. The machine context is independent of the open thread and starts at Local. Thread defaults and auto-settle go to that machine's receipted settings methods and existing index document. Profile and keep-awake use the selected machine's existing `profile.put` and `background.keepAwake` commands. The profile editor retains that target until closed. Desktop theme, tray behavior and confirmation preferences remain in `ui-state.json`. New persisted structs use serde defaults and validate restored values. Harness discovery, Honcho status, file reveals, update grants and failed-release retry remain Local.

Built-in harness version probes run only bounded `--version` commands, never prompts or authentication commands. They remove Shina thread/MCP environment variables and do not forward prompt or server arguments. Opaque ACP binaries are not executed for version discovery; script package metadata may supply a version. ACP configuration remains read-only.

No restart-continuation setting exists. Updates require empty submitted queues and no dispatchable delegated tasks before fencing new work. There is nothing to resume after validated update, and no prompt is injected into a completed turn. Crash recovery and interrupted task review retain their existing behavior.

One-process multi-server fixtures use fake release and helper implementations for grant defaults, local grant changes, busy refusal, target-selected releases, rate limits, audit records, success/rollback persistence and older protocols. Run `shina serve` from the same binary as an independent per-user process. It owns execution and durable state. Rune, and later mobile, authenticate as clients. Closing every window leaves accepted work running. This is shared access to server-owned sessions, not replication of live agent processes.

At the research baseline, `docs/captains.md`, `src/background.rs`, routines and memory persistence were absent. Slice 1 now uses their merged implementations and existing schemas.

## Process ownership and updates

Add `server.rs`, `runtime.rs`, `protocol.rs`, `client.rs`, `server_lock.rs` and `server_auth.rs`. Use Tokio/Axum for HTTP/WebSockets, existing blocking harness workers, and a single serialized runtime command loop. Replace Rune wake dependencies with an `Arc<dyn Fn()>` notification adapter; never call `State::new` headlessly because it constructs artwork and image caches.

Both legacy and server modes acquire an exclusive transaction on `<data>/server-owner.sqlite` before loading writable state. After recovery and listener readiness, atomically publish `server.json` containing `serverId`, `instanceId`, PID, start time, loopback port, protocol range, binary version and an OS-generated 256-bit bootstrap token. Restrict the directory/file to the user, including Windows ACLs. The token exchanges for a local device credential. Publish no secrets in logs or argv.

Follow KSG Code's desktop model (`apps/desktop/src/backend/DesktopBackendManager.ts`). The desktop app supervises its local server as a child process: it reads this file, attaches to a ready server if one already owns the profile, otherwise spawns `shina serve`, waits for readiness and restarts it with backoff (0.5 s growing to 10 s) if it exits unexpectedly. Simultaneous launches converge through the lock. Never kill a PID or remove a lock based only on a stale port file. A held lock with no ready listener reports recovery/unavailability. Keep harness jobs owned by the server, not the UI's kill-on-close job.

As in KSG (`apps/desktop/src/app/DesktopLifecycle.ts`), quitting the desktop app stops the server it spawned, with a 5 s grace for harnesses; on Windows and Linux closing the last window quits, on macOS the app stays in the Dock. Work then resumes through durable state and restart continuation on the next launch. A server the desktop app attached to but did not spawn keeps running. Always-on machines run a headless `shina serve` installed as an opt-in boot service with `shina service install`, like KSG's `apps/server/src/cli/service.ts` and `cloud/bootService.ts`: a systemd user unit on Linux and a LaunchAgent on macOS. KSG has no Windows service; Shina adds a per-user logon scheduled task there. The opt-in tray mode in `src/background.rs` keeps the desktop app, and so its server, alive after the window closes. Server startup must load the host's existing provider environment; never copy authentication from a UI or repository.

Keep checksum verification, explicit restart approval and rollback in `src/update.rs`. The server coordinates one update. `server.prepareRestart` refuses active/configuring/queued work, approvals and clones initially. On approval, fence new mutations and routine dispatch, broadcast draining, flush, reap idle processes, and exit. The helper waits for both server and local clients before replacing Windows executables or the Mac bundle, starts `serve`, validates readiness, then reopens clients. Timeout or save failure cancels the drain; never silently abort work. Back up the database before schema upgrades and retain it for binary rollback. Protocol-major mismatch refuses normal commands with upgrade guidance; additive minor capabilities negotiate independently.

If `src/background.rs` merges, its tray controls are clients: Open window, server status and explicit Stop server. Tray opt-in must not become the condition for keeping runs alive.

## State boundaries

Server `RuntimeState` owns projects and host paths, thread metadata, transcript projection/event log, harness/session identities, processes, lifecycle, submitted queues, approvals, tasks, captain relationships, memory and routine scheduling. Preserve process-specific approval expiry and task delivery IDs. Existing CPA-only Pi behavior and ACP capability limits remain.

Client `ClientState` owns Rune `TextEdit`, hover, pickers, selection, tabs, layout, scroll, tool/thought expansion, animation, caches and unsent editor text. Split `Tool.expanded`, `Thought.expanded` and `PiSession.queue_expanded` from durable records. Visits are explicit server commands, not whatever `active` happened to mean on one client.

Drafts stay on the device that typed them, as in KSG, which persists composer drafts client-side (`apps/web/src/composerDraftStore.ts`, zustand `persist` to localStorage) and never syncs them. Shina keeps them in local `ui-state.json`. Attachments follow that draft. Send atomically captures content into a server-owned input and clears only the matching editor revision. Stop returns unsent queue entries as recoverable inputs, never inserts text into another device's editor.

Move `Thread::apply` server-side first, preserving adapter normalization. Incrementally separate `reduce` from returned effects. Clients receive typed projection updates, not raw harness records or the execution reducer. Rune can apply a bounded batch, wake once and draw immediately without duplicating approval, queue or recovery logic.

## Protocol v1

Use JSON-RPC 2.0 over `/v1/ws`, with HTTP for blobs. Native clients use bearer headers; browser-capable clients exchange credentials over HTTP for short-lived single-use WebSocket tickets. Validate Origin. `hello` negotiates protocol major/minor, projection schema and capabilities and returns identities, versions, limits and server time.

Every mutation carries a client-generated UUID `commandId`. Persist receipt keyed by authenticated device and ID, canonical request hash, accepted/rejected status, result IDs and committed sequence. Duplicate identical requests return the receipt; changed payloads fail. An accepted receipt means durable intent, not completed provider execution. Receipt lookup resolves lost responses.

Concrete methods, with capability-gated groups introduced by later slices:

| Methods | Required inputs or result |
| --- | --- |
| `hello`, `command.get` | Versions/capabilities; command ID to receipt |
| `workspace.subscribe`, `subscription.cancel` | Workspace identity, optional workspace sequence; subscription ID |
| `thread.subscribe` | Thread, optional live sequence and stream epoch, byte budget; scoped snapshot or replay completion |
| `thread.history` | Thread, opaque older-window cursor or fragment cursor, byte budget |
| `project.put`, `project.remove`, `project.clone` | Host-local path or clone specification, project ID |
| `thread.create`, `thread.rename`, `thread.delete` | Project/harness/model/access selection; thread ID/title |
| `thread.send`, `thread.stop` | Thread, text/blob IDs, mode `prompt/steer/queue`, editor revision |

Notifications are `subscription.snapshot`, `subscription.patch`, `subscription.ready`, `subscription.resyncRequired`, `server.draining` and `auth.revoked`. Snapshot contains `{subscriptionId, epoch, seq, state, historyCursor}`. Patch contains `{subscriptionId, epoch, prevSeq, seq, upserts, removals}` with typed thread/message/tool/request/task records. Text updates replace bounded message blocks rather than resend the transcript. Workspace subscriptions carry summaries only.

For subscribe, register a bounded live buffer, capture high-water `H`, then replay committed patches through `H` or send a consistent snapshot at `H`. Replay requires matching epoch/schema and retained history, at most 128 records and 1 MiB raw/encoded. Otherwise snapshot. Send ready at `H`, then buffered live updates above `H`. Ignore duplicates; a `prevSeq` mismatch resubscribes. A cursor is per subscription scope, never a global contiguous-number assumption. Epoch survives process restarts; restore/reset creates a new epoch.

Start with 1 MiB control messages, 256 records/2 MiB outbound per subscription, 32 outstanding commands and heartbeats. Coalesce before assigning sequences. Slow clients get resync or disconnect, never block harness drains. Page snapshots/history to 256 KiB, externalize large output and fetch thumbnails lazily.

Authenticated HTTP provides `POST /v1/uploads`, offset-checked `PUT /v1/uploads/{id}`, commit and authenticated blob GET. Stream to temporary files, hash and validate before atomic promotion. Keep current image limits, eight images, 10 MiB each, 20 MiB total. Reject arbitrary server paths; expire abandoned uploads.

## Persistence and recovery

Use `rusqlite` with bundled SQLite, WAL, foreign keys and `synchronous=FULL` on a dedicated writer. Proposed tables are `events`, `thread_projections`, `projects`, `tasks`, `captains`, `queued_inputs`, `memory`, `routines`, `drafts`, `command_receipts`, `effect_outbox`, `devices` and `peers`. Events store aggregate ID, sequence, schema, command ID and payload. Store normalized projection changes and durable intent, not secret-bearing raw RPC records.

One transaction updates events/projections, receipt and outbox; publish only after commit. Effects use stable IDs. Mark dispatching before calling a provider. After process loss, an uncertain send becomes interrupted, not automatically replayed. Reconcile Pi history using existing markers; ACP without history keeps the server transcript and reports resume limits. Persist task result delivery before parent notification. Exactly-once tool actions are not promised.

Under the owner lock, validate and import `index.json`, its embedded tasks, `ui-state.json` pending inputs and attachments in one transaction. Preserve existing legacy project/collision migration in `store.rs`, session paths, captain homes and IDs. Pending acceptedness remains uncertain until history reconciliation. Import `memory.json` and routine files only against their merged versioned schema. Unknown/corrupt data aborts import without partial writes.

Record source hashes and migration completion, verify counts/references, and retain backups and every legacy file unchanged. Keep client layout/drafts in a new device-local file. Never delete legacy data or infer missing images. Pi session files remain provider-owned. Database rollback restores a matched backup, never runs an old binary against a newer schema.

## Machines, security and mobile

Give each installation a stable server UUID. Use explicit Tailscale-only listeners on the Windows PC, both Macs and Ubuntu server, or loopback behind Tailscale HTTPS. Default remains loopback; refuse wildcard/public binding. Require application auth even on the tailnet.

Pair devices/peers with short-lived, single-use, rate-limited codes approved on the target. Issue revocable per-device tokens. Store token hashes and grants server-side, outbound peer secrets in user-protected storage outside repositories. Separate `read`, `operate`, `approve`, `maintain` and `peer-delegate` scopes. MCP tokens remain thread-bound and cannot call client/admin APIs. Agents and peers cannot approve requests, elevate access modes or mint device credentials. User responses use request ID/generation compare-and-swap so two clients cannot answer twice.

A thread's authority and execution stay on its chosen server. Selecting B from client A sends creation to B, using B's projects, model availability and credentials. A client connects directly to each paired server and keys views by server/thread UUID. No filesystem path translation, automatic checkout sync, session-file copying or live migration.

A captain has one home server, which owns scheduling and memory. Remote delegation records a stable task/launch ID at home, creates a child through the peer's authorized command endpoint, then follows its result cursor. Peers never accept browser tickets as delegation credentials. Persist reconciliation and result acknowledgements; retry the same IDs after uncertain responses.

Sleeping/offline B leaves cached views labelled stale. No local fallback or queued offline approval. Only work already accepted by B can run there. Home retains pending cancellation/result delivery and reports it pending until acknowledged; it does not claim success. Retry with bounded exponential backoff, stopping on revoked auth. Closing A cannot affect B; sleeping B pauses execution until wake.

Mobile uses the same bounded projections, history paging, upload resume and device revocation. Reconnect after suspension with cursors; avoid requiring persistent foreground sockets. Later add push registration and a durable notification outbox, with opaque IDs and no prompt/tool secrets in push payloads.

## Decisions

These follow KSG Code, at the user's request.

- Every thread and captain belongs to the server where it was created, like KSG environments. New work defaults to the local desktop server. The composer's machine selector picks another linked server, and delegation can run a child on another machine that reports back to its parent. A captain meant to run around the clock is simply created on an always-on server.
- The desktop app spawns and supervises its local server and stops it when the app quits. Always-on hosts use the opt-in boot service. Login startup for the desktop app stays off.
- Drafts are per device and are not synced.
